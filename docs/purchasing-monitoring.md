# Purchasing & Inventory monitoring (WP3B)

This extends the existing platform import evaluator, `platformIncidents`, platform-only callables and `/platform` console. It adds no delivery retry, hotel operational permission, external monitoring provider or notification recipient. The production activation sequence and PR checklist are in [purchasing-monitoring-release.md](purchasing-monitoring-release.md). **Merge alone does not activate production purchasing monitoring.**

## Initial inventory

The inspected main baseline was `3108f2b83bb68c63a0fac61cc7129b00aab08a05`. Existing code already supplied scheduled import expectations, normalized import evidence, overdue/stalled detection, in-app incidents, acknowledgments, platform audit, restricted diagnostics and bounded metadata cleanup. Order dispatch, mail and scheduled-delivery journals already protected uncertain external outcomes against automatic resend. Staging already isolated provider actions and controlled multi-component releases.

The main gaps were purchasing-specific signal collection, provider-versus-business-result distinctions in the incident view, frontend/backend unexpected-error classification, bounded queue/limit observations, evaluator freshness and independent failure/absence policies. ## Coverage and operator actions

All thresholds are explicit in the environment JSON. The collector retains domain states and projects them into `healthy`, `processing`, `failed`, `stalled`, `needs-review`, `unknown`, `paused` or `simulated`. `observed` and `no-workload` describe scan coverage, not successful delivery. An AI proposal awaiting human review is explicitly classified as manual review work. It is never classified as a technically stalled parser merely because a human has not approved it. The review horizon controls how long unexpected workflow errors are eligible for new observations.

## Bounds, freshness and retention

The existing Scheduler runs every 15 minutes and evaluates up to 25 hotels per invocation using a persistent cursor. A hotel rotation takes approximately `ceil(hotelCount / maxHotelsPerRun) * 15 minutes`. Source scans also rotate persistent document-ID cursors: most sources inspect up to 30 records, dispatch/mail up to 15, orders/catalog up to 12, contract runs 20 and preflight evidence 15, each further bounded by the environment's `maxDocumentsPerSource`. The smaller dispatch/mail pages reserve reads for protected replacement-delivery evidence. A record near the end of a source collection may need multiple hotel rotations to be inspected. Expect detection within the source deadline plus that rotation delay and actual processing time. Capacity and collection growth must be reviewed before those bounds exceed the required response time.

The collector's conservative ceiling is 450 source/metadata document reads per assessed hotel before SDK transaction retries. Incident reconciliation uses at most five parallel independent transactions. Each observed incident adds transaction reads and changed incidents add writes; unchanged healthy sources do not write domain data. Existing import expectation reads, incident/history reads, retention queries and their writes are additional. Cost grows with hotel count, retained source size, scan frequency, source-query index reads, incident changes, Logging ingestion and Monitoring time series. This is a bounded design, not a measured production cost estimate.

The hotel view displays source coverage and assessment time. Partial scans remain unknown; a completed cursor cycle does not reclassify unseen business operations as successful. Synthetic coverage/backlog incidents resolve only with explicit verified same-key evidence. A later scan cannot resolve an incident merely because its source is missing. Source evidence timestamps fence stale recovery snapshots, stable transactional IDs deduplicate concurrency, and a recovered incident's next fault starts a new episode with a new acknowledgment and immutable audit event.

Worker leases prevent overlapping scheduled passes. A failed hotel's observation does not stop other hotels. The heartbeat distinguishes a successful page from a successful full hotel rotation and retains cycle failures across pages. Production release verification requires a successful nonempty full rotation started after activation, plus real log-metric evidence. Console refresh is not scheduled-execution proof.

Workflow aggregates and per-actor rate-limit metadata expire after 7 days; cleanup is bounded to 100 expired records per collection per visited hotel. Resolved incidents, audit metadata, ended support sessions and finished recovery metadata follow the existing 90-day cleanup policy. Open incidents are retained for investigation. Contract worker metadata has one fixed document. Source journals, customer files, orders, mail and stock movements retain their existing retention policy. Cleanup is best effort, not an exact deletion-time guarantee.

## Security and limits of the evidence

Platform reads check current enabled/verified Auth authority. A platform claim supplies no hotel operational membership. Browser Rules deny the new server metadata through the existing default-deny boundary. Client error ingestion additionally checks current canonical hotel membership, licensed module, workflow read permission and the existing SaaS rollout marker. Input accepts only hotel/workflow/fixed code, never arbitrary payloads, messages, stacks, file contents, URLs, attachments or recipient lists. Stable aggregates are throttled and per-actor daily capped; no session recording is included.

All business handlers run exactly once. Detached client reporting and best-effort backend observation preserve original success/error outcomes. The only explicit workflow-closure writes are incident, audit and telemetry metadata; failed tasks cannot be closed through that endpoint. Existing transport uncertainty fences and recovery permissions remain authoritative.

There is no independent heartbeat for every existing trigger, provider webhook or scheduled report. Durable jobs/receipts expose observed work; a source with no work does not prove its worker ran. The scheduled contract scan and monitoring evaluator have explicit execution evidence; broader guest/revenue reporting remains outside this purchasing scope. Console alerts require an operator to consult the console; infrastructure alerts require consulting Cloud Monitoring. External notification delivery remains unconfigured until an owner selects a recipient/channel.
